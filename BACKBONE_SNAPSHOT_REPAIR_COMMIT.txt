# BACKBONE SNAPSHOT REPAIR - COMMIT MESSAGE

## Commit Body

```
This commit fixes the "NO_SNAPSHOT on fresh install" issue by implementing
deterministic snapshot seeding on app installation and upgrade events.

ISSUE:
------
Fresh app installs show NO_SNAPSHOT on dashboard instead of AVAILABLE state,
resulting in broken first-time user experience. Root cause: snapshot pointer
missing in Forge storage when gadget resolver checks for data availability.

SOLUTION:
---------
Implement seedFirstSnapshotIfMissing() function that runs on app install/upgrade:

1. CREATED: Fresh install (no snapshot) → create + store snapshot
2. SKIPPED_VALID: Already seeded (valid snapshot) → idempotent skip
3. REPAIRED_INVALID: Corrupted snapshot exists → auto-repair and overwrite
4. FAILED: Storage error → return error with details

DETERMINISM:
------------
• Snapshot ID: buildSha-releaseVersion-seed (no Date.now, no Math.random)
• Timestamp: derived from version string (YYYY-MM-DDTHH:MM:SSZ format)
• Reproducible: same build → same snapshot ID (idempotent)
• Testable: deterministic behavior enables verification

COMPLIANCE:
-----------
• L0 snapshot schema: snapshotId, createdAtUtc, schemaVersion, metadata, data
• Jira read-only: storage-only writes, NO Jira API mutations
• Fail-closed validation: strict structure checks before accepting snapshot
• Handler wiring: manifest.yml triggers on avi:forge:installed:app

DECISION RATIONALE:

1. WHY DETERMINISTIC?
   - Enables idempotent operation (same build → same result)
   - Makes re-runs safe (already-seeded snapshots recognized)
   - Testable and debuggable (reproducible behavior)

2. WHY REPAIR SEMANTICS?
   - Handles corrupted snapshots without manual intervention
   - Fail-closed approach (invalid → auto-fix, not fail)
   - Improves reliability across installs/upgrades

3. WHY JIRA READ-ONLY?
   - Keeps snapshot creation simple
   - Only modifies ephemeral Forge storage
   - No audit trail needed for Jira itself

4. WHY L0 COMPLIANCE?
   - Matches gadget resolver expectations
   - Consistent snapshot schema across codebase
   - Enables contract-based validation

5. WHY HANDLER TRIGGER?
   - Automatic on install/upgrade (no manual action needed)
   - Integrates seamlessly with Forge app lifecycle
   - Standard Atlassian pattern
```
