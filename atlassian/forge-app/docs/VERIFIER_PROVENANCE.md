# Verifier Provenance — ECL Governance Export

## 1. What this verifier proves

The offline verifier (`tools/verify_ecl_state.mjs`) re-derives all cryptographic
hashes from the exported artifact using only:

- **Deterministic canonical JSON serialization** (FT_ECL_CORE: CANONICAL_JSON_V1 —
  keys sorted ASCII ascending, no undefined/Date/Function/non-finite/circular)
- **SHA-256** (Node.js `crypto` module, UTF-8 input)
- **No external dependencies** — verifier file is self-contained pure JavaScript

What it verifies:

| Check | How |
|-------|-----|
| Manifest hash | `SHA256(canonicalStringify(manifest))` == `payload.proofs.exportManifestSha256` |
| Payload hash | `SHA256(canonicalStringify(payloadForHash))` == `payload.proofs.exportPayloadSha256` (after stripping self-hash fields) |
| Snapshot chain integrity | For each block: `blockHash == SHA256(prevHash + payloadHash)` and `prevHash == blocks[i-1].blockHash` |
| Ledger chain integrity | For each entry: `entryHash == SHA256(prevHash + payloadHash)` and `prevHash == blocks[i-1].entryHash` |

**Self-hash stripping rule (Phase1b):** Before hashing the payload, a deep clone is
made and `proofs.exportManifestSha256` and `proofs.exportPayloadSha256` are deleted
from the clone. This ensures the hash is over payload content only — not over the
hash of the hash (circular dependency).

Exit codes:
- `0` — `VERIFIER_RESULT=FULL_PASS` (all checks passed)
- `1` — `VERIFIER_RESULT=MISMATCH` (hash mismatch detected)
- `2` — `VERIFIER_RESULT=INCOMPLETE` (required fields missing)

## 2. What this verifier does NOT prove

- **Not a blockchain audit.** This verifier does not use a public or third-party
  blockchain. Hash chains are local and only as trustworthy as the export package
  chain of custody.
- **Not a compliance certification.** Running this verifier does not certify SOC 2,
  ISO 27001, or any other standard. It is a data-integrity check only.
- **Not a real-time proof.** The verifier checks a static export snapshot. It does
  not prove that live product state is compliant at the time of verification.
- **Not tamper-evident without external custody.** If the export artifact itself is
  modified before verification, mismatches are detected — but the verifier cannot
  distinguish between an honest snapshot and a crafted one without a separate
  chain-of-custody audit trail.
- **Not a substitute for a security review.** Hash integrity ≠ correctness of
  governance policy decisions captured in the export.

## 3. Provenance rules for the golden artifact

The committed golden artifact at `docs/artifacts/golden_export_combined.json` is a
**hash-only regression fixture**. Rules:

1. **Produced by product export path** — generated by `exportPipeline.ts`
   (`ln()`) logic in a controlled sandbox environment (or the equivalent
   deterministic generator used in CI).
2. **Hash-only; no PII** — must not contain user names, email addresses, Atlassian
   account IDs, issue summaries, project names, or any customer-identifiable data.
   Use placeholder `siteId` and `snapshotId` values only.
3. **No raw Jira payloads** — must not embed raw API responses. All content must be
   either synthetic or pre-hashed.
4. **Schema change requires regeneration** — any change to the export schema
   (new fields in `ExportPayload`, new proof fields, new chain structure) requires:
   a. Regenerating the golden file with the new algorithm
   b. Re-running `node tools/verify_golden_export.mjs` to confirm `GOLDEN_VERIFY=PASS`
   c. Committing the updated golden file in the same PR as the schema change
5. **Deterministic** — the golden file must be 100% deterministic (no
   entropy/timestamps from `Date.now()` or `Math.random()`). All timestamps must be
   fixed ISO strings.
6. **Minimal** — include the minimum required fields to exercise all four
   verification checks: manifest hash, payload hash, snapshot chain, ledger chain.

## 4. How to run

### Run the full golden regression gate

```bash
node tools/verify_golden_export.mjs
```

Expected output:
```
VERIFIER_RESULT=FULL_PASS
VERIFIED_MANIFEST=1
VERIFIED_PAYLOAD=1
SNAPSHOT_CHAIN=PASS
LEDGER_CHAIN=PASS
GOLDEN_VERIFY=PASS
```

### Run the verifier against any export artifact

```bash
node tools/verify_ecl_state.mjs <path/to/export_combined.json>
```

The export file must have the shape `{ "manifest": {...}, "payload": {...} }` where
`payload.proofs` contains both `exportManifestSha256` and `exportPayloadSha256`.

### Verify the golden artifact directly

```bash
node tools/verify_ecl_state.mjs docs/artifacts/golden_export_combined.json
```

---

## 5. CI integration

The golden verify gate (`node tools/verify_golden_export.mjs`) is run as part of
`npm run build` in the build script pipeline. Any hash mismatch — due to schema
changes, algorithm drift, or file corruption — causes a build failure.
