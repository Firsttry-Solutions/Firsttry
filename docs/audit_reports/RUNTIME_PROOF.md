## What the Artifact Proves

### 1. Read-Only Operations (Proven)

The artifact demonstrates that FirstTry performs **only** read operations:

```json
"readOnlyOperations": [
  {
    "operation": "GET",
    "resource": "/rest/api/3/issues",
    "result": "SUCCESS"
  },
  ...
]
```

**Proof Anchor**: [SECURITY_SUMMARY.md#read-only-api-surface](SECURITY_SUMMARY.md#read-only-api-surface)

- All operations use GET, HEAD (read-only verbs)
- No POST, PUT, PATCH, DELETE operations
- All requests succeed (no permission errors)

### 2. Blocked Write Operations (Proven)

The artifact shows what happens if code attempts write operations:

```json
"blockedOperations": [
  {
    "operation": "POST",
    "resource": "/rest/api/3/issues",
    "result": "BLOCKED_BY_MANIFEST",
    "reason": "write:jira-work scope not declared"
  },
  ...
]
```

**Why this proves the guarantee**:
- FirstTry manifest declares only `storage:app` and `read:jira-work`
- Manifest does NOT declare write, delete, manage, or admin scopes
- Atlassian Forge enforces manifest restrictions at runtime
- Any attempt to use undeclared scope → RuntimeError

**Proof Anchor**: [SECURITY_SUMMARY.md#manifest-scope-restriction](SECURITY_SUMMARY.md#manifest-scope-restriction)

### 3. Tenant Isolation (Proven)

The artifact demonstrates workspace-scoped isolation:

```json
"tenantIsolationProof": {
  "tenant1CloudId": "ANONYMIZED_TENANT_1",
  "tenant1RequestsAllowed": 42,

  "crossTenantAttempt": {
    "result": "BLOCKED_BY_TENANT_ISOLATION",
    "reason": "key namespace enforces cloudId isolation"
  }
}
```

**Why this proves the guarantee**:
- Each tenant sees only its own data (cloudId-scoped keys)
- Cross-tenant reads are rejected automatically
- Storage key namespace prevents accidental leakage

**Proof Anchor**: [SECURITY_SUMMARY.md#tenant-isolation-enforcement](SECURITY_SUMMARY.md#tenant-isolation-enforcement)

## Change Management

### What to Do If the Artifact Changes

If the artifact differs from the canonical SHA256, you have two options:

#### Option 1: Regenerate (if timestamp changed)

The artifact includes a timestamp. If you regenerated at a different time, the timestamp will differ. This is **expected and acceptable**.

```bash
bash atlassian/forge-app/scripts/generate_runtime_proof.sh
# Compare SHA256 output
```

If only the timestamp differs, the artifact is still valid.

#### Option 2: Investigate (if content differs)

If the content structure or proof values differ, investigate:

1. **Check code changes**: Did someone modify audit event generation?
   ```bash
   git diff HEAD^^ -- atlassian/forge-app/src/audit/
   ```

2. **Check manifest changes**: Did someone add new scopes?
   ```bash
   git diff HEAD^^ -- atlassian/forge-app/manifest.yml
   ```

3. **Check tenant isolation**: Did isolation logic change?
   ```bash
   git diff HEAD^^ -- atlassian/forge-app/src/security/tenant_*
   ```

4. **Run tests**: Verify all security tests still pass
   ```bash
   cd atlassian/forge-app
   npm test -- p1_tenant_isolation.test.ts a3_immutability_guarantee.test.ts
   ```

### Approval Process for Artifact Changes

**Any intentional change to the artifact structure requires**:

1. **Security review**: contact@firsttry.run approval
2. **Code change documentation**: Commit message explaining why
3. **Test coverage**: New tests for the changed behavior
4. **Proof anchor update**: Update this document with new proof references
5. **Git history**: Artifact changes tracked in version control
